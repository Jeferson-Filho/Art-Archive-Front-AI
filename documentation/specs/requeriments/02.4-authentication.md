# Block 4 — Authentication over PostgreSQL (Firebase Discontinued)

This block covers the requirements of the new authentication system, built on top of the centralized PostgreSQL database, fully replacing Firebase Auth and the Google OAuth integrated with it in the original MVP. The system authenticates users with **email and password only** — the simplest mechanism that fulfills the product's needs, with no third-party identity provider involved.

---

**RF-026 — User authentication via email and password**

The system must authenticate users using the PostgreSQL database as the single source of truth for credentials and sessions. Email and password is the sole authentication mechanism — no login or session-verification operation depends on Firebase Auth or on any third-party identity provider (e.g., Google OAuth).

**Scenario 026.1 — Successful login**

```gherkin
Given the user has an account created in PostgreSQL
When the user logs in with their email and password
Then the system authenticates the user via PostgreSQL
And a valid session is created
And the user is redirected to the authenticated home page
```

**Scenario 026.2 — Invalid credentials**

```gherkin
Given the user attempts to log in with an email and password
When the email does not match any account, or the password is incorrect
Then the system rejects the login attempt
And no session is created
And the user sees an error message, without indication of whether the email or the password was the incorrect field
```

---

**RF-027 — Account creation**

The system must allow a visitor to create a new account using email, password, and name, persisted in PostgreSQL. There is no data continuity with Firebase — users who existed in Firebase need to create a new account in the system.

**Scenario 027.1 — Successful account creation**

> Related RFs/RNFs: RF-026

```gherkin
Given a visitor without an account provides an email, a password, and a name
When they submit the sign-up form
Then a new user is created in PostgreSQL
And they are able to log in with the email and password just registered
```

**Scenario 027.2 — Email already registered**

```gherkin
Given a visitor provides an email that is already registered in PostgreSQL
When they submit the sign-up form
Then the system rejects the account creation
And the existing account is left unchanged
And the visitor sees an error message indicating the email is already in use
```

---

**RF-028 — Logout**

An authenticated user must be able to end their session explicitly. Logging out invalidates the session so it can no longer be used to authenticate subsequent requests.

**Scenario 028.1 — Successful logout**

```gherkin
Given the user is authenticated with a valid session
When the user logs out
Then the session is revoked in PostgreSQL
And the user is redirected to an unauthenticated area of the platform
And the revoked session can no longer be used to access authenticated resources
```

---

**RF-029 — Password recovery request (Forgot Password)**

A user who cannot access their account must be able to request a password reset from the "Forgot Password" screen by providing their email. To avoid revealing which emails are registered, the system responds the same way whether or not the email exists.

**Scenario 029.1 — Reset link requested**

```gherkin
Given a user is on the "Forgot Password" screen
When they submit their email
Then the system sends a password-reset link to that email if an account with it exists
And the user sees the same confirmation message regardless of whether the email is registered
```

---

**RF-030 — Setting a new password (Change Password)**

> Related RFs/RNFs: RF-029

Following the link received from the password recovery request, the user must be able to set a new password on the "Change Password" screen. The link's token is single-use and expires after a limited time.

**Scenario 030.1 — Successful password change**

> Related RFs/RNFs: RF-026

```gherkin
Given the user opened a valid, unexpired password-reset link
When they enter and confirm a new password
Then the new password is saved in PostgreSQL
And the reset token can no longer be reused
And the user is able to log in with the new password
```

**Scenario 030.2 — Invalid or expired link**

```gherkin
Given the user opened a password-reset link that is invalid, already used, or expired
When they attempt to set a new password
Then the system rejects the request
And no password is changed
And the user sees an error message asking them to request a new reset link
```

---

**RF-031 — Session persistence**

Once authenticated, the user's session must persist across page reloads and browser restarts, without requiring a new login, until the session is revoked (logout) or expires.

**Scenario 031.1 — Session survives a page reload**

```gherkin
Given the user has a valid, non-expired session
When they reload the page or return to the platform in a new browser tab
Then the system recognizes them as authenticated
And they are not asked to log in again
```

---

> **Flag for confirmation:** this revision removes Google OAuth from the scope of this document, per the instruction to keep authentication to the simplest form (email and password). `documentation/specs/07-api-contract.md` (§5, `POST /auth/login`) and `documentation/specs/05-database.md` (`users.google_id` and its related constraints/indexes) still describe Google OAuth as a supported login option carried over from the original MVP — they are now out of sync with this document and were not modified here, since changes to those documents were not part of this request.
