# Block 3 — Screen Reader Support (ARIA)

This block covers accessibility requirements for the platform. RF-014–RF-017 apply specifically to the Insight Card, the new component introduced by the expansion. RF-018–RF-025 extend accessibility to the rest of the platform's existing screens (Home/Grid, Search, Artwork Details, Login, Sign Up, 404) and shared UI patterns (icon buttons, custom dropdowns, modals/overlays, forms), covering both semantic HTML/keyboard operability and ARIA attributes — ARIA alone cannot make a non-semantic element (e.g. a `<div>` used as a button) keyboard-operable. Screens not yet implemented (Forgot Password, Change Password, Administrative Panel) are out of scope here and will get their own accessibility requirements when built.

---

**RF-014 — ARIA label on the Insight Card**

> Related RFs/RNFs: RF-005

The Insight Card's "Context information" section must have `aria-label` or `aria-labelledby` on the region that contains it, identifying it as "Context information" for screen readers. The historical context and comparative analysis text is rendered as plain paragraphs within that single region and is **not** individually labeled — there are no internal subsections to announce.

**Scenario 014.1 — ARIA attribute present**

```gherkin
Given the Insight Card has been generated and displayed on an artwork's detail page
When a screen reader navigates to the component
Then the screen reader announces the region once as "Context information"
And the paragraph content within the region is then read continuously, with no internal subsection announced
```

---

**RF-015 — ARIA live region for loading and error states**

> Related RFs/RNFs: RF-006, RF-007

The Insight Card's loading state and error state must be automatically announced by screen readers without the user needing to navigate to the element. This must be implemented by means of an element with `aria-live="polite"`.

**Scenario 015.1 — Loading announcement**

> Related RFs/RNFs: RF-006

```gherkin
Given the screen reader user accesses an artwork's detail page
And the Insight Card is still being generated
When the loading state is displayed
Then the screen reader automatically announces that the content is being loaded
Without the user needing to move focus to the card area
```

**Scenario 015.2 — Error announcement**

> Related RFs/RNFs: RF-007

```gherkin
Given the screen reader user accesses an artwork's detail page
And the Insight Card generation fails
When the error state is displayed
Then the screen reader automatically announces the error message
```

**RF-016 — Accessible identification of the AI-disclosure notice**

> Related RFs/RNFs: RF-008, RF-014

The persistent AI-disclosure notice must be programmatically associated with the "Context information" region — e.g. via `aria-describedby` on the region pointing to the notice, or by placing the notice inside the labelled region itself — so a screen reader user encounters the disclosure as part of the Insight Card rather than relying on visual proximity or styling alone.

**Scenario 016.1 — Disclosure reachable via the region**

```gherkin
Given the Insight Card content is displayed on an artwork's detail page, whether freshly generated or retrieved from the database
When a screen reader user navigates to the "Context information" region
Then the disclosure notice "This content was generated by artificial intelligence and may contain inaccuracies." is announced or reachable as part of that region
```

**RF-017 — Accessible sources list**

> Related RFs/RNFs: RF-010

When a text block's sources are returned and displayed, they must use list semantics — native `<ul>`/`<li>` or `role="list"`/`role="listitem"` — with an accessible group name (e.g. `aria-label="Sources for context information`). When a block has no sources, no empty sources list or region is rendered.

**Scenario 017.1 — Sources announced as a list**

```gherkin
Given a text block was generated with one or more sources
When a screen reader user reaches the sources for that block
Then the screen reader identifies them as a list and announces each source as a separate item
```

**Scenario 017.2 — No sources available**

```gherkin
Given a text block was generated with no appropriate sources
When the block is displayed
Then no sources list or region is rendered for that block
And this is not announced as an error
```

**RF-018 — Semantic landmarks and page structure**

Every page (Home/Grid, Artwork Details, Login, Sign Up, 404) must use semantic HTML5 landmark elements (`header`, `nav`, `main`, `footer`) instead of generic `div`s for structural regions, so screen reader users can jump between regions. The site must also provide a "skip to main content" link as the first focusable element on the page, allowing keyboard users to bypass the header/navigation.

**Scenario 018.1 — Landmark navigation**

```gherkin
Given a screen reader user opens any page of the platform
When they use their screen reader's landmark navigation feature
Then they can jump directly to the header, main content, and footer regions
```

**Scenario 018.2 — Skip link**

```gherkin
Given a keyboard user loads any page of the platform
When they press Tab for the first time
Then focus lands on a visible "Skip to main content" link
And activating it moves focus to the page's main content region
```

**RF-019 — Accessible names for icon-only controls**

Every icon-only interactive control (e.g. the gallery's favorite/expand/contrast buttons, the image viewer's close and zoom controls, the filter panel's collapse, back-to-top, and info buttons, and the header logo link) must expose an accessible name via `aria-label` (or equivalent), since the icon alone conveys no meaning to a screen reader.

**Scenario 019.1 — Icon button announced correctly**

```gherkin
Given a screen reader user navigates to an icon-only control anywhere on the platform
When focus reaches the control
Then the screen reader announces a descriptive label for its action (e.g. "Close image", "Expand image", "Filter by classification")
And it does not announce only "button" with no name
```

---

**RF-020 — Semantic interactive elements and keyboard operability**

Elements that trigger an action or navigation (gallery image tiles, the header logo, filter chips and filter-rail items, sort-dropdown options, and text links such as "Forgot password") must be implemented as native interactive elements (`button` or `a`) rather than non-interactive elements (`div`, `span`) with a click handler. Where a native element cannot be used, the element must have an appropriate `role`, be reachable via `tabIndex="0"`, and respond to Enter and/or Space the same way it responds to a click.

**Scenario 020.1 — Keyboard activation**

```gherkin
Given a keyboard-only user tabs to an interactive element that is not a native button or link
When they press Enter or Space
Then the same action fires as if the element had been clicked with a mouse
```

**Scenario 020.2 — Reachable via Tab**

```gherkin
Given a keyboard-only user is navigating the Home page or the filter panel
When they press Tab repeatedly
Then every clickable gallery tile, filter chip, and dropdown option receives visible focus in a logical order
And no interactive element is skipped
```

---

**RF-021 — Dialog semantics and focus management for modal/overlay UI**

Overlay components that visually cover the rest of the page — the image lightbox (`imageViewer`) and the filter side panel — must be marked with `role="dialog"` and `aria-modal="true"`, and have an accessible name (`aria-label` or `aria-labelledby`). While open, keyboard focus must be trapped within the overlay, the Escape key must close it, and on close, focus must return to the element that triggered it.

**Scenario 021.1 — Opening an overlay**

```gherkin
Given the user activates a control that opens the image lightbox or the filter panel
When the overlay opens
Then it is announced as a dialog with its purpose
And keyboard focus moves inside the overlay
```

**Scenario 021.2 — Focus trap and Escape**

```gherkin
Given the image lightbox or filter panel is open
When the user presses Tab repeatedly
Then focus cycles only among the overlay's own interactive elements
And when the user presses Escape
Then the overlay closes
And focus returns to the element that originally opened it
```

**RF-022 — Custom dropdown/listbox ARIA pattern**

> Related RFs/RNFs: RF-020

The custom sort dropdowns used in the filter sections (e.g. classification, technique, period) must follow the ARIA listbox pattern: the trigger element has `aria-haspopup="listbox"` and `aria-expanded` reflecting its open/closed state, the option list has `role="listbox"`, and each option has `role="option"` with `aria-selected` reflecting the current selection. Arrow keys must move between options while the list is open.

**Scenario 022.1 — Dropdown state announced**

```gherkin
Given a screen reader user focuses a sort-dropdown trigger
When they activate it to open the list of options
Then the screen reader announces the control as expanded and identifies it as a listbox with its options
```

**Scenario 022.2 — Arrow-key navigation**

```gherkin
Given a sort dropdown is open
When the user presses the Down or Up arrow key
Then focus (or the active-selection announcement) moves to the next or previous option
And pressing Enter selects the focused option and closes the dropdown
```

**RF-023 — Form labeling and error announcement**

> Related RFs/RNFs: RF-026, RF-027

Every input on the Login and Sign Up forms must have a `<label>` programmatically associated to it via matching `htmlFor`/`id` attributes. Validation errors must be linked to their corresponding input via `aria-describedby` and must be announced to screen reader users when they appear (e.g. via `role="alert"` or an `aria-live` region), not conveyed by color or icon alone.

**Scenario 023.1 — Label association**

```gherkin
Given a screen reader user focuses an input on the Login or Sign Up form
When the input receives focus
Then the screen reader announces the input's associated label text
```

**Scenario 023.2 — Validation error announced**

```gherkin
Given the user submits the Login or Sign Up form with an invalid field
When the validation error is displayed
Then the screen reader automatically announces the error message
And the error message is programmatically associated with the invalid input
```

**RF-024 — Sitewide keyboard navigation and visible focus**

Every interactive element on the platform (links, buttons, form fields, filter controls, gallery tiles) must be reachable and operable using only the keyboard, in a logical tab order. A visible focus indicator must be present on every focusable element at all times; default browser focus outlines must not be removed (`outline: none`) without an equivalent visible replacement.

**Scenario 024.1 — Full keyboard traversal**

```gherkin
Given a keyboard-only user starts at the top of any page
When press the Tab repeatedly until reaching the end of the page
Then every interactive element on the page receives focus at some point
And no keyboard trap prevents the user from continuing to tab through or away from any element
```

**Scenario 024.2 — Visible focus indicator**

```gherkin
Given a keyboard-only user tabs to any interactive element
When the element receives focus
Then a visible focus outline or equivalent visual indicator is displayed around it
```

---

**RF-025 — Accessible error/empty/404 states**

The 404 page and the "no results" state of the Home/Search page must expose their message to assistive technology as soon as they are displayed (e.g. via a proper heading and/or `role="status"`), rather than relying on visual text and layout alone.

**Scenario 025.1 — 404 page announced**

```gherkin
Given a screen reader user navigates to a route that does not exist
When the 404 page loads
Then the screen reader announces that the page was not found
```

**Scenario 025.2 — Empty search result announced**

```gherkin
Given a screen reader user applies filters or a search term that returns no artworks
When the empty state is displayed
Then the screen reader automatically announces that no results were found
```
