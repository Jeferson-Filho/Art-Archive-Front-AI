# Non-Functional Requirements

**RNF-001 — Response time for already-persisted content**

> Related RFs/RNFs: RF-001, RF-004, RF-012, RF-013

Historical context, comparative analysis, and Alt Text are each generated, checked, and persisted independently, through their own dedicated AI API call. The **500ms** limit applies to each block's response individually, not to the combined total when multiple already-persisted blocks are returned together: for 95% of requests, the back-end's response for a given block that is already in the database must be delivered in at most 500ms, measured from receipt of the request to the sending of the response for that block (excluding client-side network latency).

**How to verify:** load test with K6 or similar against the Insight Card retrieval endpoint with data pre-populated in the database, measuring each block's response independently.

---

**RNF-002 — Maximum generation time (first visit)**

> Related RFs/RNFs: RF-001, RF-002, RF-003, RF-011, RF-013

Unlike RNF-001, this limit is a shared budget across all pending AI API calls, not a per-call limit. Historical context, comparative analysis, and Alt Text generation calls share a single **60-second** window, counted from when generation is triggered. The overall generation is only considered a timeout if none of the three calls return within this window; if at least one call returns before the deadline, its content is used normally even while the others are still pending or have failed for a different reason. The front-end must display a loading state throughout this entire period.

**How to verify:** end-to-end time measurement in a development environment with real calls to the Azure OpenAI API, covering both the case where all three calls are pending and the case where only some are.

---

**RNF-003 — Persistence reliability**

> Related RFs/RNFs: RF-004, RF-013

Once an artwork's content has been successfully generated and returned to the front-end, it must be available in the database for all subsequent requests for that artwork. Acceptable data-loss rate after successful generation: **≤1%** (99% of successfully generated blocks must be found in the database on a subsequent request).

**How to verify:** after each successful generation in tests, query the database directly to verify the presence of the record; track the persistence-failure rate against the 1% budget over a representative sample of generations (e.g. via the persistence-failure log entries described in the persistence requirement's failure scenario).

---

**RNF-004 — Compliance with WCAG 2.1 level AA across the platform**

> Related RFs/RNFs: RF-014 until RF-025

All screens and components of the platform — both the components introduced by this expansion (Insight Card, loading/error states, Alt Text) and the platform's pre-existing screens (Home/Grid, Search, Artwork Details, Login, Sign Up, 404) — must comply with the WCAG 2.1 level AA guidelines. Specifically: minimum contrast of 4.5:1 for normal text, functional keyboard navigation, semantic HTML with correct ARIA roles/attributes where native semantics are insufficient, and correct announcements via screen readers. See `02.3-aria-accessibility.md` for the detailed functional requirements.

**How to verify:** evaluation with NVDA or VoiceOver + axe DevTools during accessibility testing (doc 12).

---

**RNF-005 — API credential security**

The Azure OpenAI and Harvard Art Museums API keys must not be exposed in source code, in application logs, or in HTTP responses returned to the front-end. They must be stored exclusively in server environment variables.

**How to verify:** code review + search for key patterns in the repository before any commit.

---

**RNF-006 — Prompt versioning**

> Related RFs/RNFs: RF-002, RF-003, RF-011

The prompts used to generate the Insight Card and the Alt Text must be versioned (e.g., `v1`, `v2`), and the prompt version identifier must be stored alongside the generated content in the database, allowing tracking of which version produced each record.

**How to verify:** after generation, verify that the prompt version field is correctly filled in the database record.

---

**RNF-007 — Loading state usability**

> Related RFs/RNFs: RF-006

The Insight Card's loading state must communicate to the user that the process is in progress. The indicator must be visible without the user needing to scroll the page, assuming a screen with a minimum resolution of 1024x768.

**How to verify:** visual inspection at 1024x768 resolution during usability testing (doc 12).

---

**RNF-008 — Degraded availability without AI**

> Related RFs/RNFs: RF-007

In case of total unavailability of the AI API, the platform must remain functional for all features of the original MVP (navigation, filters, detail page with metadata). Only the Insight Card becomes unavailable, displaying an error message.

**How to verify:** simulate AI API failure and verify that the MVP's features remain operational.
