# Use Cases — Accessibility

Covers RF-014–RF-025 and RNF-004. US-008–US-010 and UC-06 are specific to the Insight Card's "Context information" region; US-011–US-018 and UC-07–UC-14 extend accessibility to the rest of the platform's screens and shared UI patterns — matching how the requirement document groups both under the same Accessibility block.

---

## User Stories

**US-008**
As a **User navigating with a screen reader**,
I want **the "Context information" section to be announced once as a single labeled region, with its AI-disclosure notice reachable as part of it**,
so that **I get the same content sighted Users get, without a confusing internal structure**.

> Related RFs/RNFs: RF-014, RF-016
> Related use cases: UC-06

---

**US-009**
As a **User navigating with a screen reader**,
I want **to be automatically told when the context information is loading or has failed, without needing to search for it**,
so that **I know the state of the page as soon as it changes, the same way a sighted User sees it at a glance**.

> Related RFs/RNFs: RF-006, RF-015
> Related use cases: UC-04, UC-06

---

**US-010**
As a **User navigating with a screen reader**,
I want **the list of sources for a text block to be announced as a proper list, and to hear nothing at all when a block has no sources**,
so that **I can browse references the same way sighted Users scan them, without being told about an "empty" list that isn't there**.

> Related RFs/RNFs: RF-017
> Related use cases: UC-06

---

**US-011**
As a **User navigating with a screen reader or keyboard**,
I want **to jump directly between the header, main content, and footer, and to skip repeated navigation with a "Skip to main content" link**,
so that **I don't have to tab through the same menu on every page**.

> Related RFs/RNFs: RF-018
> Related use cases: UC-07

---

**US-012**
As a **User navigating with a screen reader**,
I want **every icon-only button (favorite, expand, close, zoom, filter collapse, back-to-top, info) to announce what it does**,
so that **I don't have to guess the meaning of an icon I can't see**.

> Related RFs/RNFs: RF-019
> Related use cases: UC-08

---

**US-013**
As a **User navigating with a keyboard only**,
I want **every gallery tile, filter chip, sort option, and text link to be reachable and activatable with Tab and Enter/Space**,
so that **I can use the whole gallery and filter panel without a mouse**.

> Related RFs/RNFs: RF-020, RF-024
> Related use cases: UC-09, UC-13

---

**US-014**
As a **User navigating with a keyboard or screen reader**,
I want **the image viewer and the filter panel to be announced as dialogs, trap my focus while open, close on Escape, and return focus to where I opened them from**,
so that **I never get lost behind an overlay or lose my place in the page**.

> Related RFs/RNFs: RF-021
> Related use cases: UC-10

---

**US-015**
As a **User navigating with a screen reader or keyboard**,
I want **the sort/filter dropdowns to announce their open/closed state and let me move between options with the arrow keys**,
so that **I can choose a filter without a mouse and without confusion about what's selected**.

> Related RFs/RNFs: RF-022
> Related use cases: UC-11

---

**US-016**
As a **User filling in the Login or Sign Up form**,
I want **every field to have a properly associated label, and every validation error to be announced and linked to its field**,
so that **I know what to type and, if I make a mistake, what exactly went wrong and where**.

> Related RFs/RNFs: RF-023
> Related use cases: UC-12

---

**US-017**
As a **User navigating with a keyboard only**,
I want **every interactive element on any page to be reachable in a logical order, with a visible focus indicator at all times**,
so that **I always know where I am on the page and am never trapped**.

> Related RFs/RNFs: RF-024
> Related use cases: UC-13

---

**US-018**
As a **User navigating with a screen reader**,
I want **to be told immediately when a search or filter returns no artworks, or when I've landed on a page that doesn't exist**,
so that **I don't sit wondering whether the page is still loading**.

> Related RFs/RNFs: RF-025
> Related use cases: UC-14

## Detailed Use Cases

### UC-06 — Navigate the "Context Information" Region via Screen Reader

| Field                | Detail                                                                                                               |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a screen reader                                                                      |
| **Secondary Actors** | Assistive Technology, Art Archive System (front-end)                                                                 |
| **Preconditions**    | The "Context information" section is in one of its possible states: loading, resolved (one or both blocks), or error |
| **Postconditions**   | The User accesses the exact same content and states as any other User, with no barrier specific to screen-reader use |

**Main Flow**

1. The User reaches the "Context information" region, which is labeled via `aria-label`/`aria-labelledby`.
2. The screen reader announces the region once as "Context information"; the paragraphs inside are read continuously, with no internal subsection announced.
3. The AI-disclosure notice is reachable as part of the same region (`aria-describedby` or nested placement), so it's encountered without relying on visual proximity.
4. If sources are present for a block, they are announced as a list (`ul`/`li` or `role="list"`) with an accessible group name; if a block has no sources, nothing is rendered or announced for it.

**Alternative / Exception Flows**

- **1a.** The content is still loading, or generation has failed → the state is announced automatically via an `aria-live="polite"` element, without the User needing to move focus to the region.

**Acceptance Criteria**

```gherkin
Feature: Accessible "Context information" region

  Scenario: Region announced as a single labeled area
    Given the Insight Card has been generated and displayed
    When a screen reader navigates to the component
    Then it announces the region once as "Context information"
    And reads the paragraph content continuously, with no internal subsection announced
    And the AI-disclosure notice is announced or reachable as part of the same region

  Scenario: Loading and error states announced automatically
    Given the screen reader User accesses an artwork with no persisted content
    When the loading state, and later the error state (if it occurs), is displayed
    Then the screen reader automatically announces each state without the User moving focus to the card area

  Scenario: Sources announced as a list, or not announced at all
    Given a text block was generated with one or more sources
    When a screen reader User reaches them
    Then they are identified as a list, each source as a separate item
    But given a block has no sources
    Then no sources list or region is rendered or announced for it
```

> Related RFs/RNFs: RF-014, RF-015, RF-016, RF-017 · RNF-004

### UC-07 — Navigate the Platform via Landmarks and Skip Link

| Field                | Detail                                                                      |
| -------------------- | --------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a screen reader or keyboard                 |
| **Secondary Actors** | Assistive Technology                                                        |
| **Preconditions**    | The User opens any page of the platform                                     |
| **Postconditions**   | The User can move between structural regions and bypass repeated navigation |

**Main Flow**

1. The User opens any page (Home/Grid, Artwork Details, Login, Sign Up, 404).
2. The page exposes `header`, `nav`, `main`, and `footer` as semantic HTML5 landmarks instead of generic `div`s.
3. Using the screen reader's landmark navigation, the User jumps directly to any of these regions.
4. As a keyboard user, the first Tab press lands on a visible "Skip to main content" link; activating it moves focus to the main content region.

**Alternative / Exception Flows**

- None identified beyond the two flows above.

**Acceptance Criteria**

```gherkin
Feature: Semantic landmarks and skip link

  Scenario: Landmark navigation
    Given a screen reader User opens any page
    When they use landmark navigation
    Then they can jump directly to the header, main content, and footer regions

  Scenario: Skip link
    Given a keyboard User loads any page
    When they press Tab for the first time
    Then focus lands on a visible "Skip to main content" link
    And activating it moves focus to the main content region
```

> Related RFs/RNFs: RF-018 · RNF-004

### UC-08 — Operate Icon-Only Controls via Screen Reader

| Field                | Detail                                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a screen reader                                                                                                               |
| **Secondary Actors** | Assistive Technology                                                                                                                                          |
| **Preconditions**    | The User reaches an icon-only control anywhere on the platform (favorite/expand/contrast, viewer close/zoom, filter collapse, back-to-top, info, header logo) |
| **Postconditions**   | The control's purpose is understood without seeing the icon                                                                                                   |

**Main Flow**

1. The User tabs to (or is otherwise navigated to) an icon-only control.
2. The control exposes an accessible name via `aria-label` or equivalent.
3. The screen reader announces a descriptive label for the action (e.g. "Close image", "Filter by classification").

**Alternative / Exception Flows**

- **2a.** A control lacks an accessible name → the screen reader announces only "button" with no name; this is the defect this use case exists to prevent.

**Acceptance Criteria**

```gherkin
Feature: Accessible names for icon-only controls

  Scenario: Icon button announced correctly
    Given a screen reader User navigates to an icon-only control anywhere on the platform
    When focus reaches the control
    Then the screen reader announces a descriptive label for its action
    And it does not announce only "button" with no name
```

> Related RFs/RNFs: RF-019 · RNF-004

### UC-09 — Operate Non-Native Interactive Elements via Keyboard

| Field                | Detail                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a keyboard only                                           |
| **Secondary Actors** | —                                                                                         |
| **Preconditions**    | The User is on the Home page, the gallery grid, or the filter panel                       |
| **Postconditions**   | Every clickable tile, chip, and dropdown option is reachable and operable without a mouse |

**Main Flow**

1. The User tabs through the gallery tiles, filter chips, filter-rail items, sort-dropdown options, and text links (e.g. "Forgot password").
2. Elements that trigger an action are implemented as native `button`/`a` elements, or — where that isn't possible — carry an appropriate `role`, `tabIndex="0"`, and respond to Enter and/or Space exactly as a click would.
3. Every clickable element receives visible focus in a logical order; none is skipped.

**Alternative / Exception Flows**

- None identified.

**Acceptance Criteria**

```gherkin
Feature: Keyboard-operable custom interactive elements

  Scenario: Keyboard activation
    Given a keyboard-only User tabs to an interactive element that isn't a native button or link
    When they press Enter or Space
    Then the same action fires as if it had been clicked

  Scenario: Reachable via Tab
    Given a keyboard-only User navigates the Home page or the filter panel
    When they press Tab repeatedly
    Then every clickable gallery tile, filter chip, and dropdown option receives visible focus in a logical order
    And no interactive element is skipped
```

> Related RFs/RNFs: RF-020 · RNF-004

### UC-10 — Open and Operate a Modal or Overlay (Image Lightbox / Filter Panel)

| Field                | Detail                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a keyboard or screen reader                                 |
| **Secondary Actors** | Assistive Technology                                                                        |
| **Preconditions**    | The User activates a control that opens the image lightbox or the filter side panel         |
| **Postconditions**   | The User never loses their place behind the overlay, and returns exactly where they started |

**Main Flow**

1. The User activates the control that opens the lightbox or the filter panel.
2. The overlay is marked `role="dialog"` and `aria-modal="true"`, with an accessible name, and is announced as a dialog with its purpose.
3. Keyboard focus moves inside the overlay.
4. While open, Tab cycles only among the overlay's own interactive elements (focus trap).
5. Pressing Escape closes the overlay and returns focus to the element that opened it.

**Alternative / Exception Flows**

- None identified.

**Acceptance Criteria**

```gherkin
Feature: Accessible modal/overlay behavior

  Scenario: Opening an overlay
    Given the User activates a control that opens the image lightbox or the filter panel
    When the overlay opens
    Then it is announced as a dialog with its purpose
    And keyboard focus moves inside the overlay

  Scenario: Focus trap and Escape
    Given the image lightbox or filter panel is open
    When the User presses Tab repeatedly
    Then focus cycles only among the overlay's own interactive elements
    And when the User presses Escape
    Then the overlay closes and focus returns to the element that originally opened it
```

> Related RFs/RNFs: RF-021 · RNF-004

### UC-11 — Operate a Custom Sort/Filter Dropdown via Keyboard

| Field                | Detail                                                                                       |
| -------------------- | -------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a screen reader or keyboard                                  |
| **Secondary Actors** | Assistive Technology                                                                         |
| **Preconditions**    | The User focuses a sort/filter dropdown trigger (classification, technique, period)          |
| **Postconditions**   | The User can select an option without a mouse and understands the current state at all times |

**Main Flow**

1. The User focuses the dropdown trigger, which carries `aria-haspopup="listbox"` and `aria-expanded`.
2. The User activates it; the option list is exposed with `role="listbox"`, each option with `role="option"` and `aria-selected`.
3. The screen reader announces the control as expanded and identifies it as a listbox with its options.
4. The User presses Down/Up to move between options.
5. Pressing Enter selects the focused option and closes the dropdown.

**Alternative / Exception Flows**

- None identified.

**Acceptance Criteria**

```gherkin
Feature: Accessible custom dropdown

  Scenario: Dropdown state announced
    Given a screen reader User focuses a sort-dropdown trigger
    When they activate it to open the list of options
    Then the screen reader announces the control as expanded and identifies it as a listbox with its options

  Scenario: Arrow-key navigation
    Given a sort dropdown is open
    When the User presses the Down or Up arrow key
    Then focus (or the active-selection announcement) moves to the next or previous option
    And pressing Enter selects the focused option and closes the dropdown
```

> Related RFs/RNFs: RF-022 · RNF-004

### UC-12 — Fill and Submit an Accessible Form (Login / Sign Up)

| Field                | Detail                                                                                              |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a screen reader or keyboard                                         |
| **Secondary Actors** | Assistive Technology, Art Archive System                                                            |
| **Preconditions**    | The User is on the Login or Sign Up form                                                            |
| **Postconditions**   | The User understands every field and every validation error without relying on color or icons alone |

**Main Flow**

1. The User focuses an input; the screen reader announces its associated `<label>` (linked via matching `htmlFor`/`id`).
2. The User submits the form with an invalid field.
3. The validation error is displayed and linked to its input via `aria-describedby`.
4. The error is announced automatically to screen reader Users (via `role="alert"` or an `aria-live` region), not conveyed by color or icon alone.

**Alternative / Exception Flows**

- None identified beyond the two flows above.

**Acceptance Criteria**

```gherkin
Feature: Accessible form labeling and error announcement

  Scenario: Label association
    Given a screen reader User focuses an input on the Login or Sign Up form
    When the input receives focus
    Then the screen reader announces the input's associated label text

  Scenario: Validation error announced
    Given the User submits the Login or Sign Up form with an invalid field
    When the validation error is displayed
    Then the screen reader automatically announces the error message
    And the error message is programmatically associated with the invalid input
```

> Related RFs/RNFs: RF-023 · RNF-004

### UC-13 — Full Keyboard Traversal With Visible Focus

| Field                | Detail                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a keyboard only                                                |
| **Secondary Actors** | —                                                                                              |
| **Preconditions**    | The User starts at the top of any page                                                         |
| **Postconditions**   | Every interactive element on the page has been reached and operated, with focus always visible |

**Main Flow**

1. The User presses Tab repeatedly from the top of the page.
2. Every interactive element (links, buttons, form fields, filter controls, gallery tiles) receives focus in a logical order.
3. A visible focus outline or equivalent indicator is shown on each focused element; no default outline is removed without an equivalent replacement.
4. The User continues tabbing to the end of the page without encountering a keyboard trap.

**Alternative / Exception Flows**

- None identified — a keyboard trap anywhere is itself the defect this use case guards against.

**Acceptance Criteria**

```gherkin
Feature: Sitewide keyboard navigation and visible focus

  Scenario: Full keyboard traversal
    Given a keyboard-only User starts at the top of any page
    When they press Tab repeatedly until reaching the end of the page
    Then every interactive element on the page receives focus at some point
    And no keyboard trap prevents them from continuing to tab through or away from any element

  Scenario: Visible focus indicator
    Given a keyboard-only User tabs to any interactive element
    When the element receives focus
    Then a visible focus outline or equivalent visual indicator is displayed around it
```

> Related RFs/RNFs: RF-024 · RNF-004

### UC-14 — Encounter an Accessible Empty or 404 State

| Field                | Detail                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor), navigating with a screen reader                                                 |
| **Secondary Actors** | Assistive Technology                                                                            |
| **Preconditions**    | The User navigates to a non-existent route, or applies a filter/search that returns no artworks |
| **Postconditions**   | The User is informed of the state as soon as it's displayed, not only through visual layout     |

**Main Flow**

1. The User navigates to a route that doesn't exist, or applies filters/a search term with no matching artworks.
2. The 404 page or the empty-results state loads, exposed via a proper heading and/or `role="status"`.
3. The screen reader automatically announces that the page wasn't found, or that no results were found.

**Alternative / Exception Flows**

- None identified.

**Acceptance Criteria**

```gherkin
Feature: Accessible error/empty/404 states

  Scenario: 404 page announced
    Given a screen reader User navigates to a route that does not exist
    When the 404 page loads
    Then the screen reader announces that the page was not found

  Scenario: Empty search result announced
    Given a screen reader User applies filters or a search term that returns no artworks
    When the empty state is displayed
    Then the screen reader automatically announces that no results were found
```

> Related RFs/RNFs: RF-025 · RNF-004
