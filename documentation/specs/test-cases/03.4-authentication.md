# Use Cases — Account & Session

Covers RF-026–RF-031.

---

## User Stories

**US-019**
As a **User**,
I want **to log in with my email and password**,
so that **I can access my account without depending on a third-party identity provider**.

> Related RFs/RNFs: RF-026
> Related use cases: UC-15

---

**US-020**
As a **User without an account**,
I want **to sign up with my email, password, and name**,
so that **I can create an account directly in the platform's own database**.

> Related RFs/RNFs: RF-027
> Related use cases: UC-16

---

**US-021**
As an **Authenticated User**,
I want **to log out explicitly**,
so that **my session is revoked and can no longer be used, especially on a shared device**.

> Related RFs/RNFs: RF-028
> Related use cases: UC-17

---

**US-022**
As a **User who can't access their account**,
I want **to request a password reset from a "Forgot Password" screen using just my email**,
so that **I can recover access without support intervention, and without the system revealing whether my email is even registered**.

> Related RFs/RNFs: RF-029
> Related use cases: UC-18

---

**US-023**
As a **User who requested a password reset**,
I want **to set a new password from the link I received, and have that link stop working once used or expired**,
so that **I can regain access safely and the link can't be reused against me**.

> Related RFs/RNFs: RF-030
> Related use cases: UC-19

---

**US-024**
As an **Authenticated User**,
I want **my session to survive page reloads and browser restarts**,
so that **I don't have to log in again every time I come back**.

> Related RFs/RNFs: RF-031
> Related use cases: UC-20

---

## Detailed Use Cases

### UC-15 — Log In With Email and Password

| Field                | Detail                                                                                       |
| -------------------- | -------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor)                                                                               |
| **Secondary Actors** | Art Archive System, PostgreSQL                                                               |
| **Preconditions**    | The User has an account created in PostgreSQL                                                |
| **Postconditions**   | The User is authenticated with a valid session and redirected to the authenticated home page |

**Main Flow**

1. The User accesses the login screen.
2. The User enters their email and password.
3. The system authenticates against PostgreSQL, the single source of truth for credentials and sessions.
4. A valid session is created.
5. The User is redirected to the authenticated home page.

**Alternative / Exception Flows**

- **3a.** The email doesn't match any account, or the password is incorrect → the login is rejected, no session is created, and the User sees a single generic error message that does not indicate whether the email or the password was wrong.

**Acceptance Criteria**

```gherkin
Feature: Authentication via PostgreSQL

  Scenario: Successful login
    Given the User has an account created in PostgreSQL
    When they log in with their email and password
    Then the system authenticates them via PostgreSQL
    And a valid session is created
    And they are redirected to the authenticated home page

  Scenario: Invalid credentials
    Given the User attempts to log in
    When the email does not match any account, or the password is incorrect
    Then the login attempt is rejected, no session is created
    And the error message does not indicate which field was wrong
```

> Related RFs/RNFs: RF-026

### UC-16 — Create an Account (Sign Up)

| Field                | Detail                                                           |
| -------------------- | ---------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor)                                                   |
| **Secondary Actors** | Art Archive System, PostgreSQL                                   |
| **Preconditions**    | The visitor does not yet have an account                         |
| **Postconditions**   | A new user record exists in PostgreSQL and can be used to log in |

**Main Flow**

1. The visitor provides an email, a password, and a name on the sign-up form.
2. The system creates a new user in PostgreSQL.
3. The visitor is able to log in with the email and password just registered (see UC-15).

**Alternative / Exception Flows**

- **2a.** The email is already registered → account creation is rejected, the existing account is left unchanged, and the visitor sees an error message indicating the email is already in use.

**Acceptance Criteria**

```gherkin
Feature: Account creation in PostgreSQL

  Scenario: Successful account creation
    Given a visitor without an account provides an email, a password, and a name
    When they submit the sign-up form
    Then a new user is created in PostgreSQL
    And they are able to log in with the email and password just registered

  Scenario: Email already registered
    Given a visitor provides an email already registered in PostgreSQL
    When they submit the sign-up form
    Then account creation is rejected, the existing account left unchanged
    And they see an error message indicating the email is already in use
```

> Related RFs/RNFs: RF-027

### UC-17 — Log Out

| Field                | Detail                                                         |
| -------------------- | -------------------------------------------------------------- |
| **Primary Actor**    | Authenticated User                                             |
| **Secondary Actors** | Art Archive System, PostgreSQL                                 |
| **Preconditions**    | The User is authenticated with a valid session                 |
| **Postconditions**   | The session is revoked and can no longer authenticate requests |

**Main Flow**

1. The Authenticated User triggers logout.
2. The session is revoked in PostgreSQL.
3. The User is redirected to an unauthenticated area of the platform.

**Alternative / Exception Flows**

- None identified.

**Acceptance Criteria**

```gherkin
Feature: Logout

  Scenario: Successful logout
    Given the User is authenticated with a valid session
    When they log out
    Then the session is revoked in PostgreSQL
    And they are redirected to an unauthenticated area
    And the revoked session can no longer be used to access authenticated resources
```

> Related RFs/RNFs: RF-028

### UC-18 — Request a Password Reset (Forgot Password)

| Field                | Detail                                                                                              |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **Primary Actor**    | User (Visitor)                                                                                      |
| **Secondary Actors** | Art Archive System, PostgreSQL                                                                      |
| **Preconditions**    | The User cannot access their account                                                                |
| **Postconditions**   | A reset link has been sent if the account exists; the User cannot tell either way from the response |

**Main Flow**

1. The User submits their email on the "Forgot Password" screen.
2. If an account with that email exists, the system sends a password-reset link to it.
3. The User sees the same confirmation message regardless of whether the email is registered.

**Alternative / Exception Flows**

- None identified — the identical response for both cases is the requirement itself, not an alternate path.

**Acceptance Criteria**

```gherkin
Feature: Password recovery request

  Scenario: Reset link requested
    Given a User is on the "Forgot Password" screen
    When they submit their email
    Then the system sends a password-reset link to that email if an account with it exists
    And the User sees the same confirmation message regardless of whether the email is registered
```

> Related RFs/RNFs: RF-029

### UC-19 — Set a New Password From a Reset Link (Change Password)

| Field                | Detail                                                       |
| -------------------- | ------------------------------------------------------------ |
| **Primary Actor**    | User (Visitor)                                               |
| **Secondary Actors** | Art Archive System, PostgreSQL                               |
| **Preconditions**    | The User received a password-reset link (UC-18)              |
| **Postconditions**   | The password is updated and the reset token cannot be reused |

**Main Flow**

1. The User opens a valid, unexpired password-reset link.
2. The User enters and confirms a new password on the "Change Password" screen.
3. The new password is saved in PostgreSQL.
4. The reset token is invalidated and can't be reused.
5. The User is able to log in with the new password (see UC-15).

**Alternative / Exception Flows**

- **1a.** The link is invalid, already used, or expired → the request is rejected, no password is changed, and the User sees an error asking them to request a new reset link.

**Acceptance Criteria**

```gherkin
Feature: Setting a new password

  Scenario: Successful password change
    Given the User opened a valid, unexpired password-reset link
    When they enter and confirm a new password
    Then the new password is saved in PostgreSQL
    And the reset token can no longer be reused
    And they are able to log in with the new password

  Scenario: Invalid or expired link
    Given the User opened a password-reset link that is invalid, already used, or expired
    When they attempt to set a new password
    Then the request is rejected, no password is changed
    And they see an error message asking them to request a new reset link
```

> Related RFs/RNFs: RF-030

### UC-20 — Resume Session After Reload or Restart

| Field                | Detail                                                  |
| -------------------- | ------------------------------------------------------- |
| **Primary Actor**    | Authenticated User                                      |
| **Secondary Actors** | Art Archive System, PostgreSQL                          |
| **Preconditions**    | The User has a valid, non-expired session               |
| **Postconditions**   | The User remains authenticated without logging in again |

**Main Flow**

1. The Authenticated User reloads the page, or returns to the platform in a new browser tab or after restarting the browser.
2. The system recognizes them as authenticated from the existing session.
3. They are not asked to log in again.

**Alternative / Exception Flows**

- None identified — session expiry or revocation simply routes back to UC-15, not an alternate flow of this use case.

**Acceptance Criteria**

```gherkin
Feature: Session persistence

  Scenario: Session survives a page reload
    Given the User has a valid, non-expired session
    When they reload the page or return to the platform in a new browser tab
    Then the system recognizes them as authenticated
    And they are not asked to log in again
```

> Related RFs/RNFs: RF-031
